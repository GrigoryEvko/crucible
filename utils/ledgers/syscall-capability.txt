# The ledger of the rule syscall-capability: the bare syscall sites of the
# past that no SYSCALL-CAP-OK marker covers.  `python3 utils/bin/guard explain
# syscall-capability` tells the rule.
#
# One row is `PATH | - | admit | CALL TEXT | REASON`.  CALL TEXT is the line
# that holds the call, with each comment on it removed, trimmed.  It is not a
# line number, so an edit above the call moves nothing.  A row becomes stale
# only when the call changes or goes, and a stale row fails the rule with
# exit 2.  So the file drains with the code.  Two calls with the same text in
# one file share one row, and its reason covers the two.
#
# `python3 utils/bin/guard check --rule syscall-capability --emit-keys` prints
# a template row for each live site that has no row and no marker, with the
# syscalls that the line calls.  Write the capability and the function into
# the reason by hand.  A site that a `// SYSCALL-CAP-OK:` marker in its
# statement covers has no row.
#
# The REASON is the audit surface, and the rule holds it to the sites that
# the key names.  It names a syscall that the line calls.  Each
# SHOUTING_SNAKE word in it is an identifier or a macro token of that file,
# not only a comment.  Its `via <function>` clause names the function that
# holds each call: the namespaces and the classes are optional, and the word
# `and` joins more names.  Write what the line does, not what the subsystem
# around it does.
