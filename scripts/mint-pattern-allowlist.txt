# scripts/mint-pattern-allowlist.txt — §XXI scanner grandfather list.
#
# Two interchangeable entry grammars are honoured:
#
#   NAME-KEYED  path:mint_name[:check-ok]   (PREFERRED — drift-proof)
#   LINE-KEYED  path:line[:check-ok]        (legacy — fragile)
#
# where <check> ∈ {nodiscard, noexcept, constexpr, requires, ctxfit}.
# Lines beginning with '#' are comments.  A bare key (no `:check-ok`
# suffix) exempts every check for that key.
#
# ── Why name-keyed is the default ────────────────────────────────────
#
# A LINE-KEYED entry pins an exemption to a source LINE NUMBER.  Any
# edit above the mint — a concurrent agent inserting a member, a new
# `#include`, a reflowed comment — shifts the line and silently
# invalidates the entry: the real mint reads as an un-suppressed
# violation AND the now-dangling entry trips the stale-entry gate.  That
# is the exact failure mode this file kept hitting (the FIXY-U-101
# line-collapse sweep stranded 7 entries; later sweeps stranded more).
#
# A NAME-KEYED entry pins the exemption to the mint's IDENTIFIER (the
# `mint_<noun>` token on the candidate line).  The identifier is stable
# across line shifts, so a name-keyed exemption keeps tracking the same
# factory no matter how the file above it churns.  This is the fix-18
# approach applied to the mint guard: eliminate the line number as the
# drift vector entirely.  Every entry below is name-keyed.
#
# Name-keyed semantics: `path` must match the candidate's file exactly;
# the name segment matches the `mint_<noun>` identifier.  An overload
# SET sharing one name in one file collapses to a single entry — that is
# intentional: an overload set is one §XXI factory with one carve-out
# rationale (e.g. `mint_persisted_session` has three live overloads, all
# allocating, one `:constexpr-ok` entry covers them).
#
# ── Trim discipline ──────────────────────────────────────────────────
#
# Every entry is either a STRUCTURAL exemption (allocating / syscall /
# token / passkey ctor) OR a tracked migration TODO.  When a site migrates
# to canonical §XXI shape (or the scanner learns to recognize a new
# structural false-positive), the entry MUST be removed; the stale-entry
# gate fails CI if a dead entry lingers.  The goal is for this file to
# trend toward the structural-exempt minimum.
#
# The scanner learning something is worth as much trimming as a source
# fix, and on 2026-09-21 it was worth more: teaching it to read a
# concept-constrained template parameter retired 50 entries in one change,
# against the 9 that a day of source edits retired.  An entry that
# describes a scanner limitation was never an exemption, and
# "concept-constrained-param" is gone from the list above for that reason.
# Before adding an entry, ask which of the two it is.
#
# ── Carve-out categories ─────────────────────────────────────────────
#
#   `constexpr-ok` — allocating / syscall / resource-synthesizing mint
#     (or a class-method mint reading runtime state).  §XXI rule (3)
#     explicitly permits dropping `constexpr` "in favour of plain
#     [[nodiscard]] noexcept" for genuinely-allocating mints.  Examples:
#     fixy/Mmap.h `mmap(2)`, fixy/Io.h `io_uring_setup(2)`, the eBPF /
#     perf-event `perf/*` mints, the `canopy/*` gossip-state mints, the
#     class-method view mints (`mint_open_view`, `mint_compiled_view`).
#
#   `requires-ok` — a templated mint that carries no type-level constraint
#     at all.  This category used to be much larger, and 50 of its
#     entries were not exemptions: they named a mint whose gate is a
#     concept-CONSTRAINED template parameter (`template <SomeConcept T>`),
#     which the scanner could not see because it read only the literal
#     `requires` keyword.  The two spellings mean one thing to the
#     compiler, the scanner now reads both, and those 50 entries are gone.
#     A non-type parameter (`template <std::size_t N>`) parses exactly
#     like a constrained one, so the scanner settles the difference
#     against the tree's own roster of `concept` declarations rather than
#     against the node shape.
#
#   `ctxfit-ok` — a CTX-BOUND mint that takes a context no constraint
#     gates, so it accepts every context in the tree.  This is the
#     question §XXI actually asks of a ctx-bound mint, and it was
#     previously invisible: `requires-ok` conflated "carries no
#     constraint" with "carries no gate on its CONTEXT", and a mint that
#     constrained some other parameter satisfied the axis while admitting
#     any context at all.  Note that `IsExecCtx Ctx` does NOT gate the
#     context — it states that the parameter IS one.  A token mint has no
#     entry in this category, because §XXI derives its authority from a
#     parent token rather than from a context.
#
#   `noexcept-ok` — §XXI admits NO noexcept exemption: "Every mint MUST
#     be [[nodiscard]] constexpr noexcept", and only the constexpr half
#     has an escape for allocating factories.  So an entry in this
#     category is a DEFECT, not an exemption.  The category is empty, and
#     a new entry in it belongs under DEFECTS below with its remediation.
#
#   `nodiscard-ok` — a mint whose return value can legitimately be
#     discarded.  A passkey constructor is NOT in this category: the
#     guard skips `= default` declarations outright, because a
#     constructor cannot carry [[nodiscard]] and an entry describing a
#     rule the site is structurally unable to obey is not an exemption.
#
# ── DEFECTS, not exemptions ──────────────────────────────────────────
#
# An entry that reads like a category and is actually an open defect is
# the failure this whole file exists to prevent, so the open ones are
# named here rather than buried in the list.
#
# No `noexcept-ok` entry remains.  The one that stood here named
# mint_af_xdp_socket, and 2b65b669 put the keyword on the signature and
# deleted the entry.  §XXI admits no noexcept exemption, so this category
# is expected to stay empty.
#
# The 26 `ctxfit-ok` entries ARE the open-defect list now.  Each one is a
# ctx-bound mint that gates no context, and each needs a real conjunct
# rather than an entry.  They sit in their own section below with the
# remediation stated once for the set.  All 26 are in the old substrate
# that Stage D deletes; the only new-tree entry, `mint_pipeline`, was
# repaired rather than excused.
#
# An earlier revision of this file attributed that entry, and a further
# eleven entries under canopy/ and cntp/, to those trees being
# "edit-banned".  No such ban is declared in CLAUDE.md, in AGENTS.md, in
# any guard script, or in any commit message — this file was the only
# document asserting it, and the only document relying on it.  A
# justification that cites nothing but itself is not a justification, so
# the claim is withdrawn.  The canopy/ and cntp/ entries stand or fall
# on their own category, like every other entry here; the section
# headers below no longer label either tree as banned.
#
# If a per-session ownership split does make a file untouchable for a
# particular change, say so on the entry with the date and the scope,
# not as a standing property of the directory.
#
# Cross-references:
#   fixy-M-22 (#1507) — CLOSED: mint_vigil_mode_bridge gained constexpr.
#   fixy-M-23 (#1508) — CLOSED: mint_persisted_session gained noexcept on
#       all three live overloads.  constexpr-ok carve-out retained.
#   fixy-A4-027 (#1666) — CLOSED: mint_federation_admittance gained a
#       standalone [[nodiscard]]; it has no entry in this file.
#
# ── Known over-breadth in `constexpr-ok` ─────────────────────────────
#
# §XXI's constexpr escape is conditioned on the factory "genuinely
# allocating".  Several `constexpr-ok` entries name a mint that builds a
# fixed-capacity aggregate in place and allocates nothing — the canopy/
# gossip-state mints are the clearest cases.  Those entries are carrying
# a rationale that does not apply to them.  Nothing here fails on it
# today, which is precisely why it is written down: an over-broad
# category is how a real drift gets absorbed without anyone noticing.

# ── ctxfit: ctx-bound mints that gate no context ──────────────────────
#
# Every entry below is an OPEN GAP, not a structural exemption, and each
# one needs the same repair: a `CtxFits...<..., Ctx>` conjunct plus the two
# HS14 negative-compile fixtures proving it fires.  They are listed so the
# gap has a name and a count.
#
# WHAT THE OLD LEDGER SAID INSTEAD.  These sites used to carry a
# `requires-ok` entry, which reads as "the gate is a constrained parameter
# the scanner cannot see".  For the surface parameter that was true.  For
# the CONTEXT it was not: a mint constrained only on its channel surface
# takes `HotFgCtx`, `ColdInitCtx` and every other context equally, and
# §XXI's whole claim for a ctx-bound mint is that the requires clause
# verifies a CROSS-TIER FIT.  The entry named the wrong axis, so fixing the
# scanner's blind spot would have retired the entry and left the gap with
# no record anywhere.  That is why this category exists.
#
# Every entry below sits in the old substrate, which Stage D deletes; the
# port carries the gate.
#
# There WAS one new-tree entry, `include/fixy/concurrent/Pipeline.h`'s
# `mint_pipeline`, and it was repaired rather than excused.  It enforced
# the fit with an in-body `static_assert` producing `EffectRowMismatch`,
# which is a HARD error rather than a constraint, so
# `requires { mint_pipeline(bad_ctx, ...) }` answered true and no caller
# could probe it — the same defect the view mints carried until 0a14fa5c.
# The repair was one line: its clause already had a correct concept,
# `CtxFitsPipeline`, sitting unused in the same header.  The body
# assertion stayed, because deleting the concept's row conjunct was
# measured to make it fire on the same call.
